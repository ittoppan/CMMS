# Checklist ติดตามหลังเพิ่ม ModuleGuide (เมนู ระบบ & ตั้งค่า + หน้า /register)

เอกสารนี้สรุปสิ่งที่ควรทำต่อหลังจากเพิ่ม `ModuleGuide` แล้ว (อิงจากงานล่าสุด: รวมหน้า `/register`)

> หมายเหตุ: งานในรายการส่วนใหญ่เป็นการทดสอบ/กระบวนการโดยคน หรือต้องตัดสินใจร่วมทีม — ทำในโค้ดอัตโนมัติไม่ครบทุกข้อ

## 1) ทดสอบสิทธิ์/มุมมองจริงหลังล็อกอิน
- [ ] ทดสอบด้วยบทบาทอย่างน้อย: ผู้ดูแลระบบ + ผู้ใช้ทั่วไป (และบทบาทอื่นถ้ามี)
- [ ] ตรวจเมนู “ระบบ & ตั้งค่า” แสดงตามสิทธิ์ และการ์ด `ModuleGuide` แสดงผลอ่านง่าย
- [ ] ทดสอบบันทึกจริงในหน้าเสี่ยง: `/users`, `/roles`, `/settings/*` (อย่างน้อย menus/notifications/services/repair-options/design/pwa/health), `/editor/builder`, `/pages`, `/register`
- [ ] บันทึกผล: error ฝั่ง API/permission, ข้อความที่ควรปรับใน Guide

## 2) ยืนยันพฤติกรรม `/register` (ผูก LINE)
- [ ] ทดสอบ flow จริงตามสภาพแวดล้อม (LIFF/endpoint/ตั้งค่า LINE) — หน้านี้พึ่งพา API ภายนอก
- [ ] ยืนยันข้อความ/คำแนะนำใน ModuleGuide ตรงกับขั้นตอนจริง (ปรับข้อความถ้าจำเป็น)
- [ ] ตรวจเคส: ยังไม่ผูก, ผูกแล้ว, รหัสพนักงานไม่ถูกต้อง, API ล้มเหลว

## 3) กระบวนการตรวจซ้ำเป็นระยะ
- [ ] **Audit Log** (`/audit-log`): กำหนดรอบตรวจและผู้รับผิดชอบ
- [ ] **Feedback** (`/feedback`): กำหนดช่องทางสรุป/นำไปปรับปรุง
- [ ] **Notifications** (`/notifications`, `/notifications/history`) + ตั้งค่าใน `/settings/notifications`: ทดสอบกฎ/ช่องทางจริง
- [ ] **System Health** (`/settings/health`): กำหนดใครดูเป็นประจำและขั้นตอนเมื่อพบผิดปกติ

## 4) งานที่ค้างด้านความเข้มงวด (ต้องวางแผนแยก)
- [ ] ทบทวน/ออกแบบการล็อกสิทธิ์ฝั่งเซิร์ฟเวอร์จุดที่เคยพิจารณา (เช่น `public/api/v1/spare_parts.php` ตามบันทึกก่อนหน้า) — ทำเป็นงานแยกพร้อมทดสอบ

## 5) เอกสาร/การดูแลรักษา
- [ ] บันทึกให้ทีมทราบว่า `ModuleGuide` คือแหล่งคำอธิบายสั้นในหน้า และควรอัปเดตเมื่อ flow/API หลักเปลี่ยน
- [ ] (ถ้าต้องการ) ผูกรายการนี้กับ issue/tracker ภายในองค์กร
