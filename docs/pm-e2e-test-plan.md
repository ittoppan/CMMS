# แผนทดสอบ E2E / กรณีขอบเขต (Edge Cases) — โมดูล PM/AM (ใช้ข้อมูลจริง)

> เอกสารนี้เป็นแผนทดสอบเพื่อรันบนสภาพแวดล้อมที่มี **ฐานข้อมูลและผู้ใช้จริง** (staging/production ตามความเหมาะสม)  
> ข้อกำหนด: **ห้ามสร้างข้อมูลปลอมค้าง**, ห้ามแก้ DB/env/secrets/settings โดยพลการ, อย่า claim ว่าผ่านถ้ายังไม่ได้รัน, บันทึกผล “ผ่าน/ไม่ผ่าน/N/A + เหตุผล/หลักฐาน”

## 0) ข้อมูลก่อนเริ่ม
- สภาพแวดล้อม/BUILD_ID/commit ที่ทดสอบ, วันที่-เวลา, ผู้ทดสอบ, บทบาทผู้ใช้ที่ใช้ทดสอบ
- ชุดข้อมูลอ้างอิงที่ใช้ (asset, แผน PM, รอบ PM, ผู้รับผิดชอบ/ทีม, แผน meter-based ที่มีอยู่) — ระบุ ID/รหัสเพื่อย้อนรอย
- ช่องทางแจ้งเตือนที่ตั้งค่าไว้จริง (LINE/Email/Telegram) และว่ารัน `scripts/pm_reminders.php`/cron หรือไม่ (ถ้าไม่รัน ให้ระบุ N/A สำหรับเคสส่งจริง)

## 1) วงจรชีวิตรอบ PM (time-based) และ fixed schedule
**เป้าหมาย:** ยืนยันสถานะ, การคำนวณกำหนด, และรอบถัดไปไม่เกิด schedule drift

| เคส | ขั้นตอน | ผลที่คาดหวัง | หมายเหตุข้อมูลจริง |
|---|---|---|---|
| สร้าง/แก้รอบ | สร้างรอบ PM (daily/weekly/monthly/quarterly/semi_annual/yearly) กำหนด `due_date`, ผู้รับผิดชอบ/ทีม, priority, outsource/cost/duration ตามที่ schema รองรับ | บันทึกสำเร็จ (CSRF ผ่าน), แสดงผลครบ, filter/ค้นหาเจอ | ใช้ข้อมูลจริงที่ได้รับอนุญาต |
| Due/Overdue sync | เปิดอ่านรายการ/รายละเอียดเมื่อเลยกำหนด (pending + due_date < วันนี้) | สถานะสะท้อน overdue ตามข้อมูลจริง (sync ตอนอ่าน) โดยไม่แก้รอบที่ปิด/ข้าม/ยกเลิก | เปรียบเทียบกับ DB |
| ปิดงานตรงเวลา | ปิดรอบในวันที่ครบกำหนด (พร้อม checklist/ค่าที่จำเป็น) | สถานะ completed, บันทึก `completed_at/last_done_date/completed_by`; สร้างรอบถัดไปอัตโนมัติ (ถ้าเงื่อนไขเข้า) โดยฐานรอบถัดไปยึด `due_date` เดิม + cadence | ตรวจ `due_date` รอบใหม่ |
| ปิดงานล่าช้า | ปิดรอบหลังวันครบกำหนด | อนุญาตปิด, รอบถัดไปคำนวณแบบ fixed schedule (เลื่อนจาก `due_date` เดิมจนอยู่หลังวันที่อ้างอิง/ปิดจริง) — **ไม่ drift** จากวันปิดจริง | เปรียบเทียบตัวอย่างหลายรอบ |
| ห้ามปิดล่วงหน้า | พยายามปิดก่อนถึง `due_date` (ถ้า UI/API บังคับ) | ถูกปฏิเสธตามกติกา | |
| ข้าม/ยกเลิก | ข้ามรอบ/ยกเลิกตามสิทธิ์ | สถานะถูกต้อง, ไม่สร้างรอบถัดไปที่ไม่พึงประสงค์, ประวัติคงอยู่ | |
| เลื่อน/อนุมัติ (ถ้ามี flow) | ดำเนินการเลื่อน/ขออนุมัติตามที่ระบบรองรับ | สถานะ/กำหนด/ผู้อนุมัติถูกต้อง, แจ้งเตือน (ถ้ามี) ตรงเหตุการณ์ | N/A ถ้า flow ไม่มีในสภาพแวดล้อม |
| คัดลอกฟิลด์รอบถัดไป | ตรวจรอบที่ถูกสร้างอัตโนมัติ | คัดลอกฟิลด์สำคัญ/ทีม/หน่วยมิเตอร์/interval/priority/ระยะเวลา/outsource/cost ตามที่กำหนด | เทียบฟิลด์ต่อฟิลด์ |

## 2) PM ตามมิเตอร์ (CBM) — น้ำ/ไฟ/ชั่วโมง
**เป้าหมาย:** ค่าที่บันทึกจริงสะท้อนสถานะ CBM และรอบถัดไปถูกต้อง (ไม่สร้างรอบเวลาแทน)

| เคส | ขั้นตอน | ผลที่คาดหวัง |
|---|---|---|
| บันทึกค่ามิเตอร์จากหน้ารายละเอียดเครื่อง | ที่ Asset Registry → รายละเอียดเครื่อง กรอกค่า preset `kWh`/`m³`/ชั่วโมง และบันทึก | POST `asset_measurements` สำเร็จ (CSRF), ประวัติอัปเดต, สถานะ CBM refresh (`pm_plans.php?asset_id=&meters=1`) |
| หน่วย/พารามิเตอร์ตรงแผน | บันทึกค่าที่หน่วย/พารามิเตอร์ตรงกับ `meter_unit` ของแผน meter-based | CBM แสดงค่าปัจจุบัน/baseline/เป้าหมาย/คงเหลือ/สถานะตามจริง, รายการแสดงว่า “ตรงแผน” |
| หน่วย/พารามิเตอร์ไม่ตรง | บันทึกค่าหน่วยต่างจากแผน | แสดงเตือน/ไม่จับคู่ (no_reading หรือ N/A ตามตรรกะ), UI ชี้แจงให้แก้ให้ตรง |
| ไม่มีค่า/ไม่มี baseline | แผน meter-based ที่ยังไม่มีค่าที่ตรงกัน | แสดง **N/A**/คำชี้แจง ไม่ fabricate ค่า |
| ปิดงาน checksheet (meter-based) | กรอก `ค่ามิเตอร์ปัจจุบัน` ใน checksheet แล้วปิดงาน; ทดสอบกรณีเว้นว่าง | ถ้ากรอก: ใช้เป็น baseline รอบถัดไป; ถ้าเว้นว่าง: ระบบพยายามใช้ค่าล่าสุดของเครื่องตามหน่วย/พารามิเตอร์ที่ตรงกัน หรือแสดง N/A/เตือนตามที่ออกแบบ |
| รอบถัดไปของ CBM | เมื่อถึงเป้าหมาย/เงื่อนไขตามมิเตอร์ | สร้าง/พร้อมรอบตาม baseline + interval (ไม่ใช่รอบเวลาแทน) |

## 3) มุมมองวางแผนล่วงหน้า 4–8 สัปดาห์ และภาระงาน
| เคส | ขั้นตอน | ผลที่คาดหวัง |
|---|---|---|
| ช่วงเวลา 4/8 สัปดาห์ | สลับช่วงในปฏิทิน PM | จำนวนงาน/ช่วงชน-ซ้อน (คน-วัน)/peak และสรุปตามผู้รับผิดชอบ/พื้นที่คำนวณจากรอบจริงที่ยังเปิดในช่วง (ไม่รวมปิด/ข้าม/ยกเลิก) |
| ชนกำลังคน | ผู้รับผิดชอบคนเดียวมี >1 งานในวันเดียวกัน | ถูกนับเป็น “ชน/ซ้อน” และไฮไลต์ตาม UI |
| ไม่มีข้อมูลตำแหน่ง/ผู้รับผิดชอบ | งานที่ asset ไม่มี location หรือไม่ระบุผู้รับผิดชอบ | แสดงกลุ่ม “ไม่ระบุ…” หรือ **N/A** อย่างเหมาะสม ไม่ error |

## 4) แจ้งเตือน (best-effort)
| เคส | ขั้นตอน | ผลที่คาดหวัง |
|---|---|---|
| แจ้งเตือนเมื่อออกรอบถัดไป | ปิดงานจนเกิดรอบถัดไปอัตโนมัติ (มีผู้รับผิดชอบ) | พยายามส่งแจ้งเตือน (try/catch ไม่ล้ม flow) — ยืนยันผลตาม env/channel จริง หรือบันทึกว่า N/A หากไม่ตั้งค่า |
| Endpoint/CLI reminders | เรียก `POST /api/v1/pm_reminders.php` (CSRF) หรือรัน `php scripts/pm_reminders.php [--dry-run]` | รายงาน summary/scanned/users_notified/errors สอดคล้องข้อมูลจริง; `--dry-run` ไม่ส่ง; ส่งจริงขึ้นกับ env/settings |
| Dedupe/ความถี่ | รันซ้ำ/รันจาก cron หลายรอบ | อาจมีการแจ้งซ้ำ (ไม่มี dedupe ใน schema) — บันทึกพฤติกรรมและปรับความถี่ cron ตามเหมาะสม |

## 5) KPI, รายงาน และความสอดคล้อง
| เคส | ขั้นตอน | ผลที่คาดหวัง |
|---|---|---|
| ตัวเลขสอดคล้อง | เทียบ overdue/due/completed/in_progress, compliance/โหลดงาน ระหว่าง hub, calendar/lookahead, รายละเอียด, รายงาน | นิยามและจำนวนสอดคล้องกันจากแหล่งข้อมูลเดียวกัน; ต่างกันได้เฉพาะที่มีเหตุผลชัดเจน (เช่น ช่วงเวลา/การกรอง) และต้องระบุ |
| N/A เมื่อคำนวณไม่ได้ | ฟิลด์/ข้อมูลขาด (เช่น ไม่มีค่ามิเตอร์, ไม่มีเวลา/ชั่วโมงที่จำเป็น) | แสดง N/A หรือคำชี้แจงแหล่งข้อมูลขาด **ไม่ fabricate** |

## 6) สิทธิ์, ความปลอดภัย และความทนทาน
| เคส | ขั้นตอน | ผลที่คาดหวัง |
|---|---|---|
| สิทธิ์บทบาท | ทดสอบด้วยผู้ใช้หลายบทบาท (ดู/สร้าง/แก้/ปิด/ข้าม/ยกเลิก/ดูรายงาน) | อนุญาต/ปฏิเสธถูกต้อง |
| CSRF | เรียก endpoint ที่เปลี่ยนข้อมูล (POST/PUT/DELETE รวม `asset_measurements`, `pm_reminders` run) โดยไม่มี/ผิด token | ถูกปฏิเสธ (403/ตามกลไก) |
| ข้อมูลขอบเขตผิดปกติ | วันที่ไม่ถูกต้อง, ค่ามิเตอร์ไม่เป็นตัวเลข, หน่วยว่าง/ผิด, ฟิลด์บังคับขาด | validation ชัดเจน ไม่ทำให้ข้อมูลเสียหาย |

## 7) บันทึกผลและการทำความสะอาด
- บันทึก: เคส, ผล (ผ่าน/ไม่ผ่าน/N/A), หลักฐาน (ID/ภาพ/ข้อความตอบกลับโดยไม่เปิดเผย secret), BUILD_ID/commit
- **ลบ/ย้อนกลับข้อมูลทดสอบที่สร้างขึ้น** หากไม่ใช่ข้อมูลปฏิบัติงานจริง (ห้ามทิ้งค้าง)
- หากพบข้อผิดพลาด: ระบุสาเหตุ, ผลกระทบ, และข้อเสนอแก้ไข (แยกจากการแก้ DB จริงโดยพลการ)
